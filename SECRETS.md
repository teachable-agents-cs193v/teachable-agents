The project uses the following secrets:

* DATABASE_URL — Neon database connection string.
* BETTER_AUTH_SECRET — Secret used by Better Auth to sign and secure authentication sessions.
* ENCRYPTION_MASTER_KEY — Key used to encrypt and decrypt sensitive application data.
* LLM_API_KEY — Groq API key used to access the language model.

All of our production and preview secrets are stored as environment variables in Vercel, with separate values configured for each environment where required and marked as sensitive. Backup copies of ENCRYPTION_MASTER_KEY and BETTER_AUTH_SECRET are stored in the team's Bitwarden vault, which only I (Anahi) have access to. These keys are important because losing the encryption master key can make existing encrypted data permanently unreadable. DATABASE_URL and LLM_API_KEY are not backed up in Bitwarden because their credentials can be regenerated through Neon and Groq, respectively. Each team member stores development-only values in their own Git-ignored .env.local file. All .env* files are excluded from Git. Gitleaks hooks are configured on every teammate's checkout to scan for accidentally committed secrets, and CI also runs Gitleaks as an automated safeguard. Secrets are only accessed on the server and must never be exposed through client-side code or given a NEXT_PUBLIC_ prefix. Secrets must never be committed to Git or shared through chat, issues, pull requests, or other unsecured channels; they should only be shared through Vercel or Bitwarden. Chase manages Vercel configuration and the Groq API key, while Betania manages database access through Neon. The project uses Neon (teachable-agents) for its database, with the production connection configured through the pooled DATABASE_URL in Vercel. Development and tests use a local, throwaway PostgreSQL database rather than the production database. Preview currently does not have a separate database, so preview deployments cannot be used for logged-in features until one is configured. The production database connection string should never be placed in .env.local or used for local development. If database credentials need to be rotated, the plan will be to create a replacement database role, update both pooled and direct connection strings wherever they are used (including Vercel), mark the updated Vercel variables as sensitive, verify connectivity, and then remove the old role. Resetting the existing password directly could cause downtime because logins, signups, and session saves may fail until the application is redeployed with the updated credentials. For BETTER_AUTH_SECRET, generate a replacement using openssl rand -base64 32, update the relevant Vercel environments, and redeploy. As such, users in the affected environment will be logged out because the existing cookies will no longer be valid. For the LLM_API_KEY, we will generate a replacement in the Groq console, update Vercel, redeploy, and then revoke the old key to avoid interruption. If the key is missing, the application may fall back to scripted demo mode. ENCRYPTION_MASTER_KEY requires particular care, so replacing it without first re-encrypting existing data will make previously encrypted data unreadable. Before rotating it, implement a migration that decrypts existing data with the old key and re-encrypts it with the new key, or remove the existing encrypted data if the application has no real users or data to preserve. Keep the old key and its backup until re-encryption has been verified.
